# Haversine 2.0.0-alpha.1

Status: prerelease

This is the first public prerelease of the Haversine V2 line.

It is intended for compatibility testing and feedback before beta, release-candidate and stable publication.

## Highlights

- functional V2 core API with named exports;
- strict coordinate validation;
- typed distance units;
- full-precision spherical `distance()`;
- generic single-pass `nearest()`;
- Node/SSR-safe package root;
- browser Geolocation API isolated behind `haversine-geolocation/browser`;
- explicit legacy compatibility entry at `haversine-geolocation/legacy`;
- dual ESM/CommonJS package outputs;
- TypeScript declarations;
- zero runtime dependencies.

## V2 core

### distance()

```ts
import { distance } from 'haversine-geolocation';

const kilometres = distance(
  { latitude: 52.2296756, longitude: 21.0122287 },
  { latitude: 59.9138688, longitude: 10.7522454 },
);
```

The V2 core:

- validates finite latitude/longitude values;
- validates geographic ranges;
- returns full numeric precision rather than V1 presentation rounding;
- supports `m`, `km` and `mi`;
- uses a documented spherical mean Earth radius by default;
- supports an explicit custom spherical radius;
- guards the Haversine intermediate against floating-point domain drift.

### nearest()

```ts
import { nearest } from 'haversine-geolocation';

const result = nearest(origin, candidates);
```

The V2 nearest-point API:

- is generic;
- preserves the original candidate object;
- does not mutate candidates;
- uses a single pass;
- returns `undefined` for an empty collection;
- keeps the first candidate on an exact distance tie.

## Browser boundary

Browser geolocation is no longer coupled to the pure package root.

```ts
import {
  getCurrentPosition,
  isGeolocationSupported,
} from 'haversine-geolocation/browser';
```

The root package can be imported in Node and SSR environments without evaluating browser globals.

## Legacy compatibility

The historical singleton remains available during the V2 migration line.

```ts
import HaversineGeolocation from 'haversine-geolocation';
```

It is also available explicitly:

```ts
import HaversineGeolocation from 'haversine-geolocation/legacy';
```

The compatibility layer preserves important V1 semantics, including historical rounding and Earth-radius behavior.

## Toolchain and supply-chain changes

The historical Karma/Jasmine/Chrome test stack was replaced by Vitest.

The historical Webpack/Babel build stack was replaced by Vite library builds.

Measured development dependency change during modernization:

- before: 424 installed packages / 30 npm audit findings;
- after: 50 installed packages / 0 npm audit findings.

Runtime dependencies remain zero.

## Breaking changes to evaluate during alpha

The canonical V2 API intentionally changes several historical V1 behaviors:

- coordinates no longer require `accuracy` for pure math;
- malformed and out-of-range coordinates now fail explicitly;
- unknown units no longer silently fall back to kilometres;
- core distance calculations no longer apply display rounding;
- the canonical Earth-radius default differs from the historical V1 compatibility facade;
- `nearest()` returns `{ point, distance }` rather than augmenting the candidate object;
- browser geolocation has an explicit subpath;
- deep imports into historically published source files are no longer supported by the V2 package contract.

See [Migrating from V1 to V2](../migration/v1-to-v2.md) for details.

## Known prerelease expectations

This alpha is not the stable V2 release.

Before stable `2.0.0`, the project still plans to evaluate:

- alpha consumer feedback;
- supported runtime compatibility matrix;
- TypeScript compiler baseline modernization;
- API reference documentation;
- performance benchmarks;
- lint/format quality gates;
- package-size regression budget;
- additional release hardening.

## Verification before npm approval

The staged package must be reviewed before 2FA approval.

Verify at least:

- package version is `2.0.0-alpha.1`;
- npm dist-tag is `next`;
- root CommonJS import works;
- root ESM import works;
- TypeScript declarations resolve;
- `./browser` resolves;
- `./legacy` resolves;
- provenance is present after public approval.

## Feedback

Alpha feedback should focus on:

- migration friction from V1;
- ESM/CommonJS interoperability;
- TypeScript ergonomics;
- browser/SSR integration;
- numerical behavior and API semantics.

Do not treat undocumented alpha behavior as a stable compatibility guarantee.
